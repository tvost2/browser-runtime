# BENCHMARK_METHODOLOGY.md

How the numbers in `docs/COMPARISON.md` / `docs/PROFILING.md` are produced, and
what they do and do not mean.

## Every benchmark, at a glance

| script | env | workload | count(s) | warmup | frames/run | runs | metric | separates |
|---|---|---|---|---|---|---|---|---|
| `bench:compare` (`run-wasm` + `run-compare`) | **Node** | fixed fixture kernel | 4,000 | 500 | 3,000 | 1 | median, p95, p99 ms | CPU only |
| `bench:scale` (`run-scale`) | **Node** | shell scene, moderate frustum | 1k…250k | ≤120 | 200–800 | 1 | median ms, ns/entity | CPU only |
| `bench:memory` (`run-memory`) | **Node** | shell scene | 10k…500k | 30 frames | — | 1 (fresh core/size) | WASM heap MB, JS heap MB, B/entity | memory |
| `bench:wasm --profile X` (`run-wasm`) | **Node** | fixed fixture kernel | 4,000 | 500 | 3,000 | 1 | median ms | CPU, per build flag |
| `bench:native` (`native-ceiling`) | **native** (g++) | shell scene | 800…20k | 200 | 3,000 | 1 | median, p95 ms | CPU, no boundary |
| `bench:baseline` (`run-baseline`) | **Node** + real Babylon | 9 scenes on `NullEngine` | 50…7k meshes | 60 | 250 | 3 | median, p95, fps, CV, GC, heapΔ | CPU (Babylon OO) |
| `profile:pipeline` | **Node** + real Babylon | 9 scenes | 50…7k | 90 | 400 | 1 | per-phase median ms | CPU phases |
| `bench:browser` (`run-browser`) | **Chromium** WebGPU | 5 scenes, `js`+`cpp` backend | ×`BCPP_SCALE` | 60 | 250 | 1 | CPU-frame, eval, gpu ms, fps | **CPU vs GPU** |
| `test:visual` (`run-visual`) | **Chromium** WebGPU | demo `field` | 10k, 20k | frame>120 | — | 1 | structural checks + screenshot | correctness |
| `test:equivalence` (`run-equivalence`) | **native + Node** | Babylon-authored fixture | 4,000 | — | — | 1 | visible-set match, 19457 numeric checks | correctness |

**Never compare a Node ms to a browser ms** — different engines, different
timers, the browser number includes GPU submit. **Never compare across hosts** —
see `bench/results/HARDWARE.md`.

## The five things compared

| # | name | what runs | harness |
|---|---|---|---|
| 1 | Babylon original | real `@babylonjs/core` `Scene._evaluateActiveMeshes` on `NullEngine` | `bench/profile-pipeline.mjs` |
| 2 | Babylon + JS data-oriented | hand-written SoA JS kernel, same visible-set output | `bench/run-compare.mjs` (`JsBackend.mjs`) |
| 3 | C++ native | `bcpp::World::evaluate`, `-O3 -march=native`, no boundary | `native/tests/bench_world.cpp` → `bench/native-ceiling.mjs` |
| 4 | C++ / WASM | same core, `em++ -O3 -msimd128`, 1 crossing/frame | `bench/run-wasm.mjs` (`WasmBackend.mjs`) |
| 5 | C++ / WASM + real WebGPU | #4 + `Renderer` drawing the visible set | `bench/run-browser.mjs` (Chromium via Playwright) |

All five compute a **byte-for-byte identical visible set** — asserted every run
against the Babylon-authored fixture (`native/tests/fixtures/kernel_*.bin`,
generated by `native/tests/gen_fixtures.mjs` from `@babylonjs/core`).

## Workloads

`bench/scenes.mjs` (Node) and `web/harness/scene-gen.mjs` (browser) build the
same 9 shapes, deterministic per seed, scaled by `BCPP_SCALE`:

small · medium · 4000-node fixture · manyObjects · manyVisible · heavyCulling ·
cpuBound · gpuBound · manyAnimations / heavyGeometry.

## Procedure

* **warmup**: 60–120 frames discarded (JIT, shader compile, cache fill).
* **measure**: 250–3000 timed frames, `performance.now()` around the unit under test.
* **repeats**: 3–5 full setup+measure cycles (Node harness); medians aggregated.
* **perturbation**: every 7th entity's `pos.x += 0.001` per frame, so the kernel
  can't be hoisted/cached and re-uploads a realistic dirty set.
* **stats**: min, mean, median, p95, p99, stddev, CV. Median is the headline;
  CV flags a noisy run.
* **GC / memory**: `--expose-gc` + `PerformanceObserver('gc')`; heap growth over
  the measure window; `performance.memory` in the browser.

## Classifying the bottleneck (before claiming a speedup)

For each workload the harness records `evalMs`, `cpuFrameMs`, `gpuMs` and labels:

| label | condition |
|---|---|
| CPU-bound (eval) | `evalMs` ≈ `cpuFrameMs` and both > `gpuMs` |
| CPU-bound (submit) | `cpuFrameMs - evalMs` dominates (instance upload, draw record) |
| GPU-bound | `gpuMs` > `cpuFrameMs` |
| allocation-bound | GC ms or heap growth dominates the frame |
| WASM-init-bound | one-off; `wasmInitMs` reported separately, never amortized into frame time |

**A speedup in a phase is only reported as a win if that phase was the
bottleneck.** `docs/COMPARISON.md` shows "GPU-paced FPS" = `1000/max(cpuFrame,
gpuMs)` next to raw CPU-frame FPS precisely so a GPU-bound win reads as ~1×.

## What the bench host is

Intel Xeon E5-2620 v3 @ 2.4 GHz (2014), Windows 10, Node 22, g++ 16.1 (MinGW),
Emscripten 6.0.9, **no discrete GPU** (WebGPU runs on the Microsoft WARP
software adapter). Consequences:
* absolute ms are ~3× a modern laptop; **ratios are what transfer**.
* every browser scene reads CPU-bound because the software GPU is slow — the
  crossover point (scene size where C++/WASM stops helping FPS) is pushed to
  much larger scenes than on real hardware. Re-run `bench/run-browser.mjs
  BCPP_GPU=hw` on a real GPU to place it.

## Anti-gaming rules

* No microbenchmark stands alone — every kernel number has a workload behind it.
* The JS data-oriented rung is a *serious* implementation, not a strawman — if
  C++/WASM can't beat it, that's the result.
* Instrumentation overhead (`performance.now()` pairs) is measured and disclosed,
  not hidden.
* Contradicted hypotheses are published (`docs/FINDINGS.md` F-001, F-006).
